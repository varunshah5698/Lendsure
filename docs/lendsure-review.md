# LendSure – My Project Note

Varun Shah, September 2026. This is a short note on my project for my mentor.

I built LendSure because I found the idea interesting: in informal lending, people decide loans based on personal trust, and I wanted to see if that kind of judgement could be structured inside an app. The app studies a borrower and suggests whether a loan should be approved, with conditions, or declined. It never approves anything by itself. It only advises, and it always shows its reasons, so a human lender makes the final call.

The app opens with a landing page I designed to look like a real product, then a login screen. You can log in with a mobile number and a one-time password, enter directly as a guest, or register with an email id. I kept three options because I wanted anyone to try the demo without getting stuck at login. Since I had no SMS service, the mobile code just appears on the screen in demo mode. I know that is not how real apps work, but for a college demo it was the practical choice.

After login comes the dashboard, which summarises the whole portfolio: how many borrowers there are, how many fall in low, medium and high risk, how many look like possible fraud, and the average trust and confidence scores. There is also a warnings feed for things like missed repayments and sudden score drops, a money section showing disbursed versus outstanding versus repaid amounts, and a table of recently checked borrowers. Our demo data has around fifteen hundred borrowers.

The main part of the app is the borrower detail page. For each borrower it calculates a trust score out of hundred, divided into identity, finances, past loan record, community network, and behaviour. Then it runs nine fraud checks, things like duplicate phone numbers, fake-looking identity details, or a loan demand far above the borrower's income. Then it gives the decision with a suggested amount, interest rate and monthly instalment, plus extra conditions for risky cases like collateral or a guarantor. Everything carries written evidence, so no number appears without a reason next to it. There is also a simulator on the same page where you can change values and see how the decision changes, without saving anything. I added that because I felt a lender would naturally ask "what if his income were higher" and the app should answer.

I also made a small question-answer box called copilot. I should clarify it is not an AI chatbot. It is a set of fixed rules I wrote that turn common questions into data queries and quote the answers. It cannot invent numbers, but it only understands the questions I prepared for.

The rest of the app covers the loan process itself: loan requests that move from draft to approval or rejection, real loans with monthly repayment schedules, repayments that cannot double-charge on double clicks, and an investigation list for suspicious cases. The admin side lets the lender change the app's own rules, like risk cutoffs and interest ranges, without touching code, and manage access keys. There is also a market section with live prices and news headlines, which falls back to sample data with a clear label when the outside services are down.

Technically, the backend is Python with FastAPI and a simple SQLite database file, no heavy layers in between. The scoring mixes a trained gradient-boosting model with hand-written rules in equal parts, and every saved result records which model version produced it. The frontend is React with Vite. The whole thing is packed into one container and deployed on Render, with a second setup on Vercel. The app talks to the outside world for market prices and news headlines, for which it needs a free news key, and optionally an email account for sending login codes. All of that happens on the server, so no secret ever reaches the browser.

Data-wise, the backend has close to a hundred small endpoints grouped around health checks, login, dashboard numbers, borrower search and analysis, document uploads, loan requests and repayments, cases, admin controls, network graphs, warnings, notifications, and market data. The database has around twenty tables holding borrower profiles, their monthly financial history, documents, every analysis with its reasons, the audit trail of all actions, loan and repayment records, notifications, api keys, and app settings. A few leftover tables from my first version still sit in the same file unused.

And now the honest part, the flaws. My first version and my rebuilt engine both live in the same codebase, and I never cleaned out the old half, which will confuse anyone reading it. The single-file database cannot handle real concurrent use, and committing it into git was a lazy decision I regret. Login is demo-grade: codes on screen, tokens in browser storage, limits kept in server memory. My training data is synthetic, made by my own script, so the high accuracy number partly means the model agrees with my generator, and the one-in-three wrong fraud flag rate is the number I actually worry about. Demo borrowers mix into normal lists with no separate environment. There is not one automated test in the project, and there is no continuous integration. If I got one more month, I would delete the dead code first, move to Postgres, write tests around the scoring logic, and fix login properly, in that order.

That is my project, as honestly as I can put it. It works end to end as a demo, and the audit trail behind every decision is the part I am proudest of, but I would not call it production-ready.
