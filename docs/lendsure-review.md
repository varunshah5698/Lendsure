# LendSure – Project Report

Varun Shah, September 2026. This note is for my mentor review. It explains my project in simple words: what it does, what it is made of, how data flows through it, and where it still falls short.

## 1. Features of the application

LendSure is a web application that helps a lender decide whether to give a loan to a borrower, and if yes, on what terms. It is meant as decision support, not automatic approval. Every suggestion the app gives comes with reasons and proof attached, so a human can always check why the app said what it said.

A new visitor first sees a landing page that introduces the product. From there they go to the login screen. There are three ways to enter. One, type a mobile number and verify with a one-time password. Since this is a student demo with no real SMS service connected, the password simply appears on the screen. Two, enter as a guest with one click, with limited access. Three, register with an email id and password, verify the email with a code, and then log in normally, with forgot-password and reset options. A lender login stays valid for seven days and a guest login for one day.

After login the user reaches the dashboard, which gives the full picture of the lending portfolio in one screen. Right now the demo data has about fifteen hundred borrowers. The dashboard shows how many fall in the low, medium and high risk groups, how many look like possible fraud, and how many are waiting for verification. It also shows the average trust score and average confidence across the portfolio. Below these numbers there is an early warnings feed, which flags things like missed repayments, sudden drops in a borrower's score, and high fraud signals. There is also a portfolio section showing total money disbursed, money still outstanding, and money repaid, plus a table of recently analysed borrowers.

The borrowers page is a searchable list of every borrower. You can search by name, and filter by risk level, verification status, city, and job type, and sort by trust score or loan amount. Opening any borrower takes you to the detail page, which is the most important screen in the whole app. It shows a trust score out of hundred, split into five parts: identity, financial behaviour, past loan history, community network, and general behaviour, each with its own points and a one-line reason. Then there is a fraud check against nine rules, things like duplicate phone numbers, fake-looking identity details, asking for a loan more than ten times the income, mismatch between stated income and documents, suspicious documents, past defaults, too many applications in a short time, and self-recommendations. Then comes the actual lending decision: approve, approve with conditions, or decline, along with the suggested loan amount, interest rate, monthly instalment and duration. Risky cases get extra conditions like collateral, a guarantor, or the loan split into parts. Every number on this page carries a confidence value and a written evidence trail, and the full history of actions on that borrower is visible below.

There is also a what-if simulator on the same page. You can change values like income or loan amount and re-run the analysis just to see what happens, without saving anything. It uses the same calculation engine, so the results are genuine.

The copilot is a question-answer box where you can ask plain-English questions about the portfolio and get answers from live data. I want to be clear that this is not a chatbot or language model. It is a fixed set of rules I wrote, which convert common questions into database queries and quote the results back. So it can never invent numbers, but it also only understands the kinds of questions I prepared it for.

Beyond single-borrower analysis, the app handles the full loan process. A loan request starts as a draft, gets submitted, and then a lender can approve it, reject it, send it back asking for more information, or withdraw it. Approving a request creates an actual loan with a month-by-month repayment schedule. Repayments are recorded against that schedule in a way that duplicate clicks cannot charge twice. There is also a cases section, which is basically an investigation list: you open a case on a suspicious borrower, attach findings, and close it when resolved.

The admin section has four pages. The overview page is a command centre with decision statistics, pending reviews, and recent activity. The policy page lets the admin change the app's own rules at runtime, like where the risk cutoffs sit, what interest ranges apply to each risk group, and when a case needs manual review, without touching code. The keys page creates and revokes per-lender access keys for programmatic use. The model page shows how the machine learning model is performing.

The financial intelligence section is like a small market terminal built into the app. It shows live market prices from a free public finance source, news headlines about the economy, a scrolling ticker, a market heat map, a currency converter, and pages on the economy and credit environment. There is a watchlist and alerts too. When the outside data sources are unreachable, the app falls back to built-in sample data and clearly labels it as such. It never shows stale or sample data pretending it is live.

Finally there are supporting touches: a notifications bell with a live stream of new warnings, a keyboard shortcut palette to jump to any page, and a simulations page with ready-made demo scenarios. If the backend server is down, the frontend says so openly instead of failing silently.

## 2. Tech stack

The backend is written in Python using the FastAPI framework, running on a server called uvicorn. The database is SQLite, which is just a single file on disk, accessed with plain SQL queries. There is no heavy database layer in between. The machine learning part uses a common Python library for a model called gradient boosting. It was trained on fifteen hundred synthetic borrower profiles, each described by about fifty features, plus around fifteen extra ratios my code computes, like debt compared to income and repayment capacity. The trained model and its accuracy numbers are stored as files alongside the code. When the app scores a borrower, it mixes the model's probability half-and-half with a set of hand-written rules, so the final result is stable and every input always produces the same output. Each saved analysis records which model version was used, so results stay auditable later.

The frontend is built in React with a build tool called Vite, page navigation handled by React Router, animations by a motion library, and the 3D visuals on the landing page by a three-dimensional graphics library. Styling is plain CSS files, one per component, with no design framework. All communication with the backend is simple same-domain web requests collected in a single helper file, so the browser never needs secret keys.

On the subject of keys and configuration: the app reads its settings from environment variables. There is a demo-mode flag that controls whether one-time passwords are shown on screen. There is an optional key for a free news service that enables real headlines. There is an optional email account and app password for sending real email codes; without them the codes are just printed in the server log for demo purposes. Lenders who want programmatic access get personal API keys from the admin page. These are stored only as irreversible hashes and passed in a request header. All outside services are contacted from the server only, never from the browser, so no secret ever reaches the user side.

For deployment, the whole thing is packed into a single container: one stage builds the frontend, the next stage runs the Python server, which serves both the data API and the built pages. The same code deploys to Render through a blueprint file, and to Vercel through a services configuration that splits the frontend and backend but keeps them on one domain, with data requests routed to the backend and everything else to the frontend. On my own machine it runs with a single start script on port eight thousand.

## 3. Endpoints and database schema, in plain words

The backend exposes close to a hundred endpoints, which are just the named addresses the frontend calls to get things done. Rather than listing them all, which would read like a phone book, here is what they cover, group by group. There are health checks that report whether the database, the model, the network analysis and the market data are alive. There is a full auth group: requesting and verifying mobile codes, guest entry, email registration and verification, login, logout, forgot and reset password, and checking the current session. There is a dashboard group giving portfolio counts, averages and monthly trends. There is a borrower group for listing, searching, filtering and viewing profiles and their financial history, plus running and reading analyses, evidence, recommendations, risk history and audit trails. There is a simulation endpoint for what-if runs that are never saved. There is a documents group for uploading, downloading and verifying proofs. There is the loan lifecycle group: creating and listing loan requests, moving them through submit, review, approve, reject and withdraw steps, viewing created loans, and recording repayments. There is a cases group for opening, listing and resolving investigations. There is an admin group for the command-centre overview, statistics, live policy changes, model information, audit logs, approval queues, active sessions, access keys, background jobs and demo scenarios. There is a graph group for borrower networks, connection paths and clusters. There is an intelligence group for warnings, portfolio aggregates and model monitoring, plus the copilot question endpoint. There is a notifications group including a live event stream. And there is a finance group of about seventeen endpoints for market overview, prices, news, economy pages, watchlist, alerts, briefings and portfolio impact. A few older endpoints from the first version of the code still exist but are no longer used by the frontend.

The database holds around twenty tables, all inside one SQLite file of about twelve megabytes. In plain terms, it stores: borrower profiles with dozens of fields each; six months of monthly income, expense and debt history per borrower; uploaded documents and their verification status; every analysis ever run, with scores, decision, suggested terms, the model's probability, the reasons, a snapshot of the inputs, and the model version; the written evidence lines behind each analysis; a permanent audit log of who did what; the app's tunable policy settings; hashed API keys; loan requests with their approval status; created loans with repayment schedules and recorded repayments; background jobs with retries; notifications and an append-only event log that feeds the live stream; investigation cases; per-borrower repayment performance that feeds back into future scores; uploaded file contents; and a log of model probabilities. A few small structural upgrades apply themselves automatically when the app starts. Separately, the same file also contains an older set of tables from the first version of the project, which the current code mostly ignores.

## 4. Flaws in the application and what I think should be done

The most embarrassing structural problem is that there are effectively two versions of the app inside one codebase. The old tables and endpoints from my first attempt still exist next to the new engine, and both get created at startup. A newcomer cannot tell which half is real. The first cleanup I would do is delete the old half completely and keep a single dashboard endpoint.

The database choice is the biggest real risk. A single SQLite file cannot handle concurrent writes properly, I committed a twelve-megabyte binary database into git which pollutes every update, there is no backup story, and on serverless hosting the data simply resets. It was the right call for a zero-setup student demo and the wrong call for anything beyond that. The proper fix is moving to Postgres with real migrations, generating demo data with a seed script, and never committing the database file again.

Authentication is demo-grade and I know it. Passwords shown on screen, login tokens kept in browser storage where malicious scripts could steal them, request limits kept in server memory so they vanish on restart, and access keys that never expire. For a lending product this is the part that worries me most. Sessions should move to secure cookies, keys need expiry and limited scopes, and limits need shared storage.

I also want to be upfront about the machine learning numbers, because they look better than they are. The training labels are synthetic, produced by my own data script, so a high accuracy score partly means the model agrees with my generator, not with the real world. The more honest number is precision around two-thirds, meaning roughly one in three flagged defaults would be wrong, and that is the number that matters when real money is involved. The half-rules half-model mixing ratio was my own choice, not a tuned value, and there is no retraining pipeline or automated checking. If my mentor asks one difficult question, I hope it is this one.

Smaller but real issues: demo and simulation borrowers sit in the same tables as everything else and appear in normal lists, with no separate environment and no reset button. There is not a single automated test anywhere, backend or frontend, and the frontend is plain JavaScript with no type checking, so refactoring is frightening and the 3D landing bundle is far too heavy. There is no continuous integration, no code checks on push, and the free hosting tiers either sleep or forget data. Before showing this to anyone outside a review, my minimum would be automated tests around the scoring logic, Postgres, and one genuine health alert.

To close: the app works end to end, and the part I am most serious about is that every decision carries its reasons, evidence and model version with it. Most lending demos skip that entirely. But I would never call this production-ready, and the list above is exactly the order I would fix things in.
